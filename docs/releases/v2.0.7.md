# v2.0.7 - V1 Remaining Limits Configuration

> Development prerelease. This release is published from \dev\, may receive
> rapid follow-up changes, and is not selected by the default \latest\ image.

## Summary

v2.0.7 moves the V1 compatibility path's remaining hardcoded limits into
deployment environment variables. Response size limits, timeout values, and the
multipart memory buffer are now read once at startup, validated with explicit
range checks and timeout relationship rules, and require a restart to change.

The startup validation ensures that \IMGPROXY_REQUEST_TIMEOUT\ is strictly less
than \V1_GENERATION_TIMEOUT\, preventing configuration errors that would cause
all dynamic transformations to fail.

This release does not add a database schema version, change an HTTP or upload
API, or change an image-processing recipe.

## Changes

### V1 response and timeout limits

- \V1_DYNAMIC_MAX_RESPONSE_BYTES\ bounds the dynamic transformation response.
  Default 100663296 (96 MiB), range 1 MiB to 512 MiB.
- \V1_BACKGROUND_MAX_RESPONSE_BYTES\ bounds the background format conversion
  response. Default 33554432 (32 MiB), range 1 MiB to 256 MiB.
- \V1_GENERATION_TIMEOUT\ sets the total generation timeout for imgproxy
  operations. Default 35s, range 5s to 5m.
- \IMGPROXY_REQUEST_TIMEOUT\ sets the HTTP client timeout for imgproxy
  requests. Default 30s, range 5s to 5m, and it **must be less than**
  \V1_GENERATION_TIMEOUT\.
- \V1_MULTIPART_MEMORY_BYTES\ sets the Gin multipart form memory buffer.
  Default 8388608 (8 MiB), range 1 MiB to 64 MiB.

### Configuration validation

- Added startup validation for all five new variables with explicit range
  checks.
- **Critical validation**: The startup validation rejects configurations where
  \IMGPROXY_REQUEST_TIMEOUT >= V1_GENERATION_TIMEOUT\ with a clear error before
  connecting to MySQL or Redis. This prevents silent failures where every
  dynamic transformation would timeout.
- The timeout relationship ensures that imgproxy has time to complete and return
  an error before the caller's context deadline expires.

### Hardcoded constant removal

- Removed constants \1DynamicMaximumResponseBytes\ (96 MiB),
  \1BackgroundMaximumResponseBytes\ (32 MiB), and \1GenerationTimeout\ (35s)
  from \internal/handler/public_handler.go\.
- The \PublicHandler\ now stores the complete \ImageV1Config\ and uses it for
  all limit checks and timeout values.
- The imgproxy HTTP client timeout is set from
  \1Limits.ImgproxyRequestTimeout\ instead of a hardcoded 30s.
- The Gin router's \MaxMultipartMemory\ is set from
  \cfg.ImageV1.MultipartMemoryBytes\ in \cmd/server/main.go\.

### Observability

- The startup summary now logs one additional line with the five new V1 limits:
  \1_dynamic_max_response_bytes\, \1_background_max_response_bytes\,
  \1_generation_timeout\, \imgproxy_request_timeout\, and
  \1_multipart_memory_bytes\.

### Deployment example

- \ackend/.env.example\ documents every new variable with comments explaining
  that they are startup-only limits, are validated, and are never exposed
  through the administrator API.

## Installation

Development images must be pulled explicitly:

\\ash
docker pull jaykserks/summerain:dev-v2.0.7
\
Equivalent exact development tag:

\\	ext
jaykserks/summerain:dev-2.0.7
\
The moving \dev\ tag also points to the newest successful development build.
\latest\, \main\, and stable semantic-version aliases are not changed by this
release.

No database migration or API migration is required when upgrading from v2.0.6.

## Known Limitations

- These limits are read once at startup; changing them requires a restart.
- The V1 path's response size limits and generation timeout are now
  configurable, but the default values remain unchanged from v2.0.6 and earlier
  versions.
- The complete fixed image recipe remains a server-side concern and is planned
  for a later release (Phase 3).
- Animated image support remains planned for a later release.
