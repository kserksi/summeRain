# v2.0.10 - Frontend Follows Server Upload Policy

> Development prerelease. This release is published from `dev`, may receive
> rapid follow-up changes, and is not selected by the default `latest` image.

## Summary

v2.0.10 makes the browser upload pipeline read the recipe client hints added in
v2.0.9 instead of relying on build-time constants. The effective concurrency
and source-size limits are now the minimum of the server hint, the device
capability, and the frontend safety cap, so an operator can lower browser-side
work from the server without shipping a new frontend, while a slow or
memory-constrained device keeps its own lower bound. A server that omits the
hints keeps the previous behavior exactly.

The recipe version is no longer a frontend constant: the client echoes the
server's version in the manifest and reprocesses persisted results when it
changes.

## Changes

### Effective upload limits

- `client_pipeline_concurrency` and `client_active_session_concurrency` size
  the upload pipeline and the active server-session gate. Both stay within the
  frontend caps of 2 and 4.
- `client_max_native_concurrency` is combined with the device capability (half
  the reported hardware concurrency, 1 to 2), so weak devices never process
  with more workers than they can sustain.
- `max_source_bytes` replaces the fixed 15 MiB pre-check and is applied both
  when files are added and again during preflight, so a file added before the
  recipe arrived is still rejected under the server policy.
- A missing hint keeps the shipped default, which is what an older server
  expects. A hint that is present but unusable (zero, negative, fractional, or
  not a number) falls back to the cap and raises one warning toast naming the
  fields instead of ignoring the misconfiguration silently.
- The frontend never raises a limit above the server value or above its own
  caps.

### Dynamic recipe version

- Removed the hardcoded `2.0.0` from the native processor, the WASM worker,
  the preflight check, the shared types, and recipe parsing.
- The client still rejects a recipe whose pipeline version or variant geometry
  it cannot produce, and the error now reports the server's `recipe_version`
  and `pipeline_version`.
- Persisted processing results are discarded and regenerated when the server's
  recipe version changes. Upload-queue recovery, leases, and retry semantics are
  unchanged.

## Installation

Development images must be pulled explicitly:

```bash
docker pull jaykserks/summerain:dev-v2.0.10
```

Equivalent exact development tag:

```text
jaykserks/summerain:dev-2.0.10
```

The moving `dev` tag also points to the newest successful development build.
`latest`, `main`, and stable semantic-version aliases are not changed by this
release.

No database migration or API migration is required when upgrading from v2.0.9.

## Known Limitations

- The hints remain advisory: the server still validates every upload
  independently, and a server that does not send them keeps the previous
  browser behavior.
- The root README still describes the default pipeline concurrency;
  documentation polish is scheduled with the deployment phase.
- Animated image support remains planned for a later release.
