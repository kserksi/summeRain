# v2.0.8 - Image Recipe File and Generated Schema SQL

> Development prerelease. This release is published from `dev`, may receive
> rapid follow-up changes, and is not selected by the default `latest` image.

## Summary

v2.0.8 moves the fixed image policy out of the Go constants and environment
variables into a server-side recipe file, and adds a generator that renders the
MySQL schema into explicit SQL for production deployments.

The recipe file now owns the variant geometry, the pixel and byte limits, the
accepted source formats, and the `recipe_version` that browser uploads must
send. The container bakes the default at `/app/config/image-recipe.json`, the
binary embeds the same default, and `IMAGE_RECIPE_FILE` plus
`IMAGE_RECIPE_REQUIRED` control the lookup. A missing file falls back to the
embedded default unless it is required; an unreadable, malformed, or
out-of-range file stops startup before MySQL is contacted.

`V2_RECIPE_VERSION`, `V2_MAX_PART_BYTES`, and `V2_MAX_PIXELS` are no longer
read; move those values into the recipe file. The defaults are unchanged, so an
unmodified deployment behaves exactly as v2.0.7.

## Changes

### Image recipe file

- Added the default recipe at `backend/internal/config/image-recipe.json`,
  embedded into the binary with `go:embed` and copied into the image at
  `/app/config/image-recipe.json`.
- Added `IMAGE_RECIPE_FILE` (default `/app/config/image-recipe.json`) and
  `IMAGE_RECIPE_REQUIRED` (default `false`).
- The recipe declares `pipeline_version`, `recipe_version`, `max_pixels`,
  `max_part_bytes`, `supported_source_mime_types`, and the four fixed variants
  (`master`, `gallery`, `admin`, `publish_source`).
- Code-level bounds stay in code: `pipeline_version` must be 2, the source MIME
  list must be a non-empty subset of the five supported formats, `max_pixels`
  must stay between 1 MP and 100 MP, `max_part_bytes` between 1 MiB and 64 MiB,
  variant dimensions between 1 and 4096 pixels, and quality between 1 and 100.
  A recipe can tighten these values but never exceed them.
- Variant validation, source MIME acceptance, part-size and pixel limits, and
  the `/api/v1/uploads/recipe` response now read the recipe instead of code
  constants. The response shape is unchanged.
- The startup log prints one `image_recipe_*` line with the source, version,
  limits, and variant summary; credentials never appear.
- The recipe stays outside the administrator API: recipe keys are rejected by
  the existing configuration allowlist.

### Generated schema SQL

- Added `backend/cmd/schema-migration-gen` and
  `scripts/generate-sql-migration.sh`.
- `bash scripts/generate-sql-migration.sh baseline_schema` writes
  `backend/migrations/<UTC timestamp>_baseline_schema.up.sql` and immediately
  verifies it.
- Generation runs on a disposable database that the tool creates and drops on
  `SUMMERAIN_SCHEMA_DSN`; it never touches an existing database.
- Verification applies the file to an empty database and requires the running
  bootstrap to leave the schema unchanged, which proves the snapshot matches
  the GORM models and every checksummed migration. The check also runs as
  `go test ./cmd/schema-migration-gen/...` when `SUMMERAIN_SCHEMA_DSN` is set.
- Committed `backend/migrations/20261003_122900_baseline_schema.up.sql`
  containing all 17 tables.

### Deployment example

- `backend/.env.example` documents the two new variables and drops the three
  variables the recipe replaced, and the dependency-lock verification asserts
  the new lines.

## Installation

Development images must be pulled explicitly:

```bash
docker pull jaykserks/summerain:dev-v2.0.8
```

Equivalent exact development tag:

```text
jaykserks/summerain:dev-2.0.8
```

The moving `dev` tag also points to the newest successful development build.
`latest`, `main`, and stable semantic-version aliases are not changed by this
release.

No database migration or API migration is required when upgrading from v2.0.7.
Move any custom `V2_RECIPE_VERSION`, `V2_MAX_PART_BYTES`, or `V2_MAX_PIXELS`
values into the recipe file before deploying.

## Known Limitations

- The generated SQL is a complete schema snapshot for empty databases.
  Incremental `ALTER TABLE` generation for existing databases is not part of
  this release; existing databases keep upgrading through the additive
  checksummed runner.
- The recipe is read once at startup; changing it requires a restart and a
  `recipe_version` bump.
- The frontend still sends a fixed `recipe_version` until the later client
  configuration phase; the default recipe keeps the two in sync.
- Animated image support remains planned for a later release.
