# v2.0.6 - Startup Performance Configuration

> Development prerelease. This release is published from `dev`, may receive
> rapid follow-up changes, and is not selected by the default `latest` image.

## Summary

v2.0.6 moves the backend performance limits that require a restart into
deployment environment variables. Every limit is read and validated once at
startup, is never writable through the administrator API, is never returned to
the frontend, and is summarized in the startup log without credentials.

A configuration error now stops the process before it connects to MySQL or
Redis, so an invalid deployment fails fast instead of starting with surprising
resource behavior.

This release does not add a database schema version, change an HTTP or upload
API, or change an image-processing recipe.

## Changes

### Startup-only limits

- `MAX_JSON_BODY_BYTES` bounds ordinary JSON request bodies. Default 1048576,
  range 1 KiB to 16 MiB.
- `V2_INIT_MAX_JSON_BYTES` bounds the V2 upload manifest. Default 65536, range
  1 KiB to 1 MiB, and it must not exceed `MAX_JSON_BODY_BYTES`.
- `V2_BATCH_STATUS_MAX_JSON_BYTES` bounds the batch status request. Default
  16384, range 1 KiB to 256 KiB, and it must not exceed `MAX_JSON_BODY_BYTES`.
- `V2_MAX_ACTIVE_SESSIONS_PER_USER` bounds concurrent V2 upload sessions per
  user. Default 8, range 1 to 32.
- `V1_DYNAMIC_GENERATION_CONCURRENCY` sizes the V1 dynamic transformation
  semaphore. Default 2, range 1 to 16.
- `V1_DYNAMIC_GENERATION_QUEUE_DEPTH` sizes the V1 waiting queue. Default 4,
  range 0 to 64.
- `V1_BACKGROUND_FORMAT_CONCURRENCY` sizes the V1 background format worker.
  Default 1, range 1 to 8.

### Wiring and observability

- The V1 dynamic and background semaphores are created from the validated
  configuration at startup.
- The V2 active-session limit is enforced from configuration instead of a code
  constant.
- The global JSON middleware and the V2 upload handlers use the configured body
  limits.
- The startup log prints one non-sensitive summary line per configuration
  group. Credentials, secrets, and connection strings are never logged.

### Deployment example

- `backend/.env.example` documents every new variable, and the dependency lock
  verification asserts their presence.

## Installation

Development images must be pulled explicitly:

```bash
docker pull jaykserks/summerain:dev-v2.0.6
```

Equivalent exact development tag:

```text
jaykserks/summerain:dev-2.0.6
```

The moving `dev` tag also points to the newest successful development build.
`latest`, `main`, and stable semantic-version aliases are not changed by this
release.

No database migration or API migration is required when upgrading from v2.0.5.

## Known Limitations

- These limits are read once at startup; changing them requires a restart.
- V1 response-size limits and the generation timeout remain code constants and
  are planned for a later release.
- The complete fixed image recipe remains a server-side concern and is planned
  for a later release.
- Animated image support remains planned for a later release.
